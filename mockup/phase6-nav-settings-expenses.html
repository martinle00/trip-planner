Item 1 — Add-place returns to the panel head; the FAB is deletedcorrects Phase 5

Phase 5 shipped a single sticky FAB (.map-add-fab-wrap) after real use of the original panel-head button was rejected as "too slim." In production, at the map's real size (min(70vh,560px), not the mockup's old 280px demo box), the FAB reads as bulky and sits awkwardly near/over the map instead of reading as chrome. Fix, per the user's decision (over the reviewer's recommendation to promote it into the sticky day quick-nav instead): delete .map-add-fab-wrap entirely and put a single "Add place" button back in .panel-head, top-right beside the "Map" title — exactly the placement already approved in mockup/header-nav-hierarchy.html's #v3-condense frames. That file's mapPanelFillerHTML() is the source for the markup below, unchanged.
The keyboard/AT reachability gap is knowingly re-opened, not solved. Once the panel head scrolls out of view, a keyboard-only or screen-reader user has no way to reach Add-place without scrolling all the way back up — the same gap header-nav-hierarchy.html flagged and the FAB briefly worked around. This is an accepted trade-off, decided by the user: it's where the button lived before, it matches the approved header mockup, and the sticky-bar alternative keeps a control pinned in chrome this phase is otherwise trying to slim down. Do not "fix" this by adding a second Add-place control — that recreates the exact redundancy Phase 5 item 2 existed to remove. See PHASE6.md's Decisions section and trap #3.
No-new-chrome mitigation: two identically-hidden skip links, not a second button. A visually-hidden link, the first focusable thing in the Map panel, jumps focus straight to the panel-head Add-place button on activation — the same well-understood "skip to content" idiom used for skip-to-main links, invisible until it receives keyboard focus (.skip-to-add below: clipped off-screen at rest, slides into view on :focus-visible). It adds zero permanent visual chrome — a sighted mouse user never sees it exist. A second copy of the same link comes after the pin list in DOM/tab order — added in review round 1 to close the gap the first round of this file honestly flagged as unaddressed (round-1 ux-reviewer suggestion, non-blocking but taken). This is a tab-order claim, not a spatial one: both copies share the identical position:absolute; top:8px; left:8px placement inside the scrolling panel, so the second one doesn't visually sit down by the pins — the instant it receives focus, the browser scrolls the panel back to the top to bring it into view, and it appears in exactly the same spot the first one did. The saving is entirely in how many Tab presses it takes to reach it (right after the pin list, not back at the very start), not in where it visually shows up. Neither is a second visible Add-place affordance, so trap #3 isn't re-triggered: both are inert until they receive keyboard focus, at which point they render identically (same class, same clipped/reveal treatment, both jump to the one real button). Tab into the frame below and press Tab once to see the first appear; tab all the way through the pin list to reach the second — watch the panel scroll back to the top when it does. Try it for real, it's genuine markup, not a screenshot.

Honest limit, still not a full fix: two fixed skip-link stops help "just arrived on the tab" and "just reached the bottom of today's pin list," but a user parked in the middle of a long list still has to tab past whichever stop is nearer rather than jump from exactly where they are. A bare single-letter keyboard shortcut (e.g. "a") was considered and rejected: several screen readers reserve unmodified letter keys for their own browse-mode navigation (headings, landmarks, form fields), so a global "a" shortcut would collide with the exact assistive technology this is meant to help. A modifier-based shortcut (e.g. Alt+Shift+A) is a possible follow-up, not solved here.

Item 3 — Map day quick-nav: short numeric date on mobile

Chips today read the full dayLabel ("Day 2 · Mon 9 Nov"), which elongates and breaks the chip row at narrow widths. Fix: a new fmtShortNumeric(iso) in lib/dates.ts — `${d.getDate()}/${d.getMonth()+1}`, no leading zeros, matching the existing parse-as-local-date convention — renders "9/11", "10/11" on mobile only. Trap #4: the chip's full text is today its entire accessible name (only the wrapping group carries an aria-label). The full label is kept, clipped with the same .visually-hidden technique used everywhere else in this codebase — never display:none'd.
Markup: two spans, one clipped, one aria-hidden — not two separate rules per breakpoint. Every chip always renders both a .chip-date-full span (the complete dayLabel text) and a .chip-date-short span (the numeric form), in the DOM at all times. Desktop shows the full span and display:none's the short one (pure decoration duplicate, so it's fine to remove outright for everyone there). Below 719px that flips: the short span becomes visible and is marked aria-hidden="true" (it's now the visual duplicate), while the full span gets the .visually-hidden clip — present, unclipped in the accessibility tree, invisible on screen. Net effect: the chip's accessible name is always the complete "Day 2 · Mon 9 Nov" form, on both viewports, regardless of which text is visually showing.

Item 4 — mobile route node: fix the strikethrough and clipped names

Root cause is CSS painting order, not a styling miss. Per CSS2.1's painting order, in-flow inline text (step 5) paints before a positioned descendant at z-index:0 (step 6) — so .route-node .line (absolutely positioned, z-index:0) always paints over .route-city, regardless of DOM order. Desktop never shows it because top:11px puts the line at dot height, spatially clear of the text below; mobile's flex-direction:row + top:50% puts the line dead centre through the letters. Phase 5's 74px mobile node width also left only ~59px for the label after the dot and gap, hence "Zhangjiajie" clipping hard.
The fix is structural, not cosmetic — two changes, both load-bearing. (1) Mobile reverts to the same stacked layout as desktop (dot above, label below, flex-direction:column) instead of Phase 5's row layout — this alone puts the line back at dot height, spatially clear of the text, same as desktop. (2) The node widens from 74px to 92px (within the 88–96px range PHASE6.md calls for), giving the label real room. On top of both, the base .route-node .line rule changes from z-index:0 to z-index:-1 globally (not just in a mobile override) — this moves the line into CSS2.1's step 2 (negative stacking contexts), which paints before any in-flow content, block or inline. That makes the fix hold regardless of layout: even if some future change reintroduces a row layout or repositions the line, it can no longer paint over text by construction. The stacked layout fixes today's bug; the z-index change is what stops it from being able to recur.

After — fixed (92px, stacked layout, line at dot height, z-index:-1)

Item 7 — fix the By-person bar's math and groupingcorrects Phase 5

Two real defects. Math: "By category" sizes bars as amount / budget.total (share of the whole trip). "By person" sizes them as sum / byPersonMax (share of the top payer) — same visual widget one card apart, two different scales. A person covering 90% of the trip and the largest of several small payers can render as an identical full-width bar. Fix: r.sum / budget.total * 100, keeping the existing Math.max(4, …) legibility floor. Grouping: item 6 moving companions into Settings resolves the second defect for free — By-category and By-person are now adjacent, no CRUD card wedged between them. Not changed: the avatar-in-label-slot and the shared jade fill — both stay exactly as documented in index.css.
Made concrete below with two scenarios, same total trip budget. Scenario A: one payer covers most of the trip. Scenario B: several payers each cover a small, similar share. Under the old (buggy) math both scenarios' top bar renders at the same near-full width, because each is scaled against its own top payer. Under the fixed math the two scenarios look visibly different, because both are scaled against the same fixed reference (the trip total) — which is the entire point of a shared-scale bar chart.

Item 8 — per-member colour, a constrained swatch set

Schema: TripMember.color?: string. UI: pick-one-of-6, applied to the member avatar ring and member chip only. Not a free colour picker — an arbitrary user hue can't be pre-verified against the -soft-ink rule. Hues were chosen to avoid the --jade/--gold zones and avoid exact overlap with the --d-* day/city palette; every -soft/-soft-ink pair is contrast-measured in both themes below and written up in DESIGN-SYSTEM.md.
The By-person bar stays jade — this is the one rule item 8 must not break. Items 9–11 — expense sharing: attach-to, who it covers, paid-by prompt

Three related schema/UI changes to the expense form and rows, demoed together since they touch the same form. 9: "Attach to" becomes a select of city names (or "Whole trip") — Expense.dayId is dropped, Expense.city?: string added; an unresolvable/legacy value degrades to "Whole trip", never throws. 10: "Covers" — everyone, one person, or a subset (coversMemberIds?: ID[], absent = everyone). 11: toggling an expense to paid now prompts for a payer; toggling back to unpaid never prompts; the add-expense form gains an "already paid" option.
Judgement call: the empty-coversMemberIds ambiguity is resolved by the interaction, not by render logic. PHASE6.md flags an explicit empty array as "meaningful-but-degenerate" and asks for a documented choice. This mockup's Covers control makes an explicit empty array unreachable: deselecting the last remaining member snaps the control straight back to "Everyone" mode (which writes undefined, not []). That normalises the ambiguity away at the interaction layer instead of adding a special case to every reader of coversMemberIds. Flagging this for the reviewer specifically because it's a judgement call, not a spec requirement — the alternative (treat [] as "everyone" in render logic, and allow it to exist) is equally defensible and touches fewer interaction states.
Paid-toggle prompt reuses the Settings modal's component, not a new pattern — a compact .overlay/.modal asking "Who paid?" with one tap per member, plus "Mark paid without a payer". Toggling to unpaid never opens it. With zero members defined (trap #8), toggling on skips the prompt entirely and marks paid with no payer — there's nothing to pick, so nothing is asked.
Interactive — try it: edit an expense's Attach-to/Covers, add a new one with "already paid" checked, toggle paid on an unpaid row
