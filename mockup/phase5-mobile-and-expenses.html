Item 2, revised — one canonical Add-place, sized and placed per breakpoint supersedes the shipped v1

This section replaces the original item 2 design in place (same anchor, same file) — that design shipped, passed review + QA, and is now live in MapPanel.tsx/index.css, but the user rejected it after seeing it in the real app: "too slim," and its location "poor compared to previous iterations." The ask this time is explicit — sizing AND location should differ between desktop and mobile, not just font-size at a smaller width. What's unchanged from the shipped version, and NOT up for debate again: still exactly ONE Add-place affordance on the Map tab (PHASE5 locked decision), still a real keyboard-focusable button in a position:sticky wrapper (not position:fixed — see the shipped version's reasoning, still valid), still mounted right after the map box, before the legend. What changes: the button's own size, shape and screen position now genuinely differ by breakpoint.
Recap — what's being replaced. The shipped control: btn btn-primary btn-sm, icon + "Add place" label, identical at 390px and on a 1400px desktop window, sitting bottom-left under the map. Shown at both breakpoints below for comparison — this is the "too slim" the user is reacting to.

Desktop (≥720px): bigger, fully labelled, same slot. Left-aligned under the map, same sticky-wrapper mechanism as before, but sized well past this app's own base .btn scale (15px 28px padding, 15px/700 label, 19px icon — vs. the shipped 6px 12px/12.5px) with a stronger resting shadow (--shadow-md, lifting to --shadow-lg on hover) so it reads as a deliberate call-to-action next to the map, not a stray pill underneath it. Desktop has no thumb-zone or bottom-dock pressure, so the extra size costs nothing — there's no competing bottom chrome to crowd. This directly answers "too slim": same location, genuinely bigger, genuinely louder.
Mobile (<720px): icon-only 48px circle, right-aligned, stacked directly above Auto-plan. This is the genuine location change, not just a size change — and it's the hard part of this brief, so here's every option weighed, not just the one picked:
  • Rejected — absolute, inside the map, next to or above Auto-plan. This was the FIRST instinct ("stack it in the map's own overlay layer") and it's exactly wrong: Auto-plan is position:absolute inside .map-container-outer, which is a plain, non-sticky block. Anything absolutely positioned in there disappears the instant the map itself scrolls out of view — precisely the reachability failure the panel-head button had, and precisely why the sticky wrapper exists at all. Putting Add-place there would silently reopen PHASE5 trap #2.
  • Rejected — bottom-left, the shipped slot, just bigger. Keeps the same containing block and mechanism (safe), but doesn't answer "location should differ" honestly — and bottom-left asks a one-handed thumb to reach across the full screen width, which is worse ergonomics than necessary when there's a better answer available.
  • Rejected — docking into .map-day-quicknav (the sticky day-chip sub-bar; explicitly offered as an option to weigh). Attractive at first — it's already position:sticky, already proven, already sits right under the tabbar. Rejected anyway because that bar is conditionally rendered, {cityDays.length > 0 && ...} — making it the sole home for the ONLY Add-place control would mean a city with zero days (an edge case, but a real one: nothing in TripRepository guarantees cityDays.length > 0 for every city that can be selected) loses Add-place entirely. Not worth the risk for a control this load-bearing.
  • Picked — stay in the existing sticky wrapper (safe, already proven), just re-aligned right and stacked above Auto-plan. Same DOM position, same containing block, same mechanism that already passed review once — the only things that change are justify-content (left → right) and the button's own shape/size. Bottom-right is normally the prime one-handed thumb zone, and it's already "spent" on Auto-plan — so this stacks Add-place 56px above it rather than opening a second zone elsewhere on the screen. The pair reads as one deliberate cluster ("the map's floating actions live here"), Auto-plan (secondary, exploratory) below Add-place (primary, and now visually louder by virtue of being a filled circle vs. a smaller pill) above it.
One control, not two. Both renderings are the same <button aria-label="Add place"> — the visible label (.btn-label) is clipped below 720px using the exact .btn-collapsible pattern item 1 already established in this file (reused, not reinvented, per DESIGN-SYSTEM §4), and aria-label="Add place" stays on the element itself either way, so the accessible name never depends on which breakpoint clipped what. CSS-only divergence: one @media (max-width:719px) block changes size/shape/alignment; no second DOM node, no duplicate button anywhere in the tree.

Two bottom-region states, both designed for, not just the empty one. Compare the two frames at the same scroll position: with no staged changes, the FAB's mobile bottom offset only has to clear the tab dock (unchanged from the shipped version's own clearance math). With the Save bar present — which is ALSO position:sticky; bottom:0, scoped to the whole panel, so it can be on screen from scroll 0 with no scrolling required — the FAB additionally clears the bar via --map-save-bar-clearance, a new custom property this design introduces (see the CSS comment above .map-save-bar). The accepted trade-off (shipped version, code review round 2): retained here, not closed. A sighted user scrolled past the legend into pin-detail/Save-bar territory still has no visible Add-place control until they scroll back up, at both breakpoints — unchanged from what's live today. Keyboard/AT reachability is unaffected either way (Tab reaches the button in DOM order regardless of its sticky/static state at that moment; the browser scrolls a focused element into view on focus) — trap #2's actual requirement was always about that, not about sighted visibility, and it holds here exactly as it did before. Closing it would require moving the wrapper to be a direct child of <section class="panel"> (sibling to .map-layout, same scope .map-day-quicknav and .map-save-bar already use) so its containing block spans the WHOLE scrollable panel instead of just the map+legend column — which is a real, considered option, not a dismissed one. It was left out of THIS revision because it's a structural change orthogonal to what was asked (sizing and per-breakpoint location), it multiplies the Save-bar-collision surface this section already had to solve once (the FAB would then need --map-save-bar-clearance for its ENTIRE reachable range, not just the narrow window where both happen to be stuck at once), and closing it is not blocking anything — the gap is unchanged from what already shipped and passed review. Flagging it explicitly, as asked, rather than silently inheriting it: if the reviewer wants it closed now, it's a same-shaped follow-up, not a rethink.

Item 3 — mobile-succinct route strip

fmtCompactRange ("7–9 Nov") plus a two-line node reads cramped at 390px, especially once several legs are visible at once. Below 719px, route-nodes drop to a single-line, city-name-only pill.
City-only, but the date is clipped — not removed — from the accessible name. This deliberately differs from the existing desktop is-condensed treatment of the same element (src/index.css: .route-date{ display:none } there, for everyone, sighted and AT alike). Two reasons it's not copied verbatim to mobile: (1) desktop's condensed state is transient — scroll up and the date comes back for everyone; the mobile-succinct state is permanent at that viewport width, so a screen-reader user has no scroll-triggered "escape hatch" back to the fuller announcement the way a desktop user does. (2) desktop's is-condensed city name gets a title attribute so a sighted mouse user can still recover a clipped city name on hover — there is no touchscreen equivalent of hover, so mobile has no sighted-recovery path either if content is fully dropped. Given both of mobile's usual "it's fine, there's a fallback" arguments don't hold, this keeps .route-date in the DOM and uses the same .visually-hidden-style clip already used throughout this codebase (not display:none) — a VoiceOver/TalkBack user still hears the full "Shanghai, 9 to 15 November", a sighted user just sees "Shanghai". Flagging this explicitly for the reviewer to push back on if the desktop precedent is judged to be the more consistent choice instead.

Item 6 (stretch) — per-person totals

Included, not deferred. See the "By person" card inside the Budget demo above — the decision-note below explains why it was a clean fit.
Why this made the cut instead of being deferred. Once 4–5 land, the data needed is already sitting on every expense (paidBy) and the conversion logic already exists and is already reused elsewhere on this exact panel (the "By category" card immediately above it uses the identical bar/track/amount layout) — this is a second data slice through already-computed numbers, not new UI language or a new fetch. It reuses convert() per expense exactly like the existing summary totals (PHASE5 trap #4: never sum raw amounts across currencies), and excludes no-rate expenses from the bars the same way the summary cards already flag them ("1 expense excluded (no rate)"-style note, not a silent drop). Empty state: no companions yet → the card doesn't render bars, it shows one line pointing back at the members card above.
