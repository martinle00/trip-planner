The problem, in one sentence

Today the primary section tabs (Map / Places / Itinerary / Budget) sit fourth in the header stack — below trip identity, a row of six utility buttons (Export, Import, sync pill, theme toggle, Auto-plan, Sign out), and the city-timeline route-strip. On the design system's stated primary device size (390px phone), that's enough chrome to push the tabs below the fold before any content loads. All three variants below try to raise the tabs' position without crowding them into an already-full row. Each has a dashed gold line in its mobile frame marking roughly where the fold sits on a compact phone with browser chrome visible (∼560px tall viewport, e.g. iPhone SE) — scroll position 0, nothing scrolled yet. If the tabs are below that line, the reorder hasn't actually solved the problem for that class of device.

Every frame is interactive within its own scope: tap a route-strip city or a tab to see the active state move. Tap Toggle light / dark in the bar above to check both themes (this mockup only has one theme switch, shared by every frame on the page, to keep comparisons apples-to-apples). The Preview: simulate offline toggle up there does the same for the offline banner (App.tsx renders it above the topbar, non-sticky, whenever the device has no connection) — it's a real state that adds height to exactly the stack being stress-tested here, so it's included as a worst-case check across every frame rather than assumed away.

Status: Variant 3 (bottom tab bar on mobile, top tabs on desktop) was reviewed, approved, and picked. The three-way comparison below is kept as-is for the record. A follow-up request came back specifically about its desktop side — the Map panel's day-filter chips and "Add place" button scroll out of view well before the map itself gets much room, since the header above them doesn't give any space back as you scroll. That's addressed in a new section, “Variant 3 refinement — condensing header (desktop)”, right after Variant 3 below. Mobile is untouched by that follow-up.

Variant 1 — reorder the stackrecommended

Title row → Tabs → route-strip → utility actions row. Nothing is merged or hidden — the DOM order changes so the primary nav becomes the second thing on the page instead of the fourth, and the utility row (used far less often) drops into normal flow below it.
Route-strip placement: fused with the primary-nav layer, not identity. The route-strip is described in code as the primary city selector — a second, orthogonal nav (which leg of the trip), not trip metadata. Once tabs are promoted to their own sticky layer, the strip reads more naturally grouped with them ("choose a section, then choose a leg") than orphaned under a now-title-only topbar. So it moves into the .primary-nav-block sticky unit directly under the tabs, and stays sticky — the city switcher doesn't lose its always-on-screen availability while scrolled, only the (rarely used) utility row does. An alternative considered — making the strip non-sticky too, to save even more vertical space — was rejected: that would regress a working always-visible city switcher for a marginal space gain, trading a frequently-used control for a rarely-used one's convenience.

Variant 2 — slim the utility row on mobile

Same DOM order as today. Below ~640px, Export / Import / Sign out and the sync pill collapse to icon-only (label kept in the DOM, visually hidden — the exact technique the sync pill already uses on its own under 380px; this variant just fires it at 640px instead, for every collapsible item at once). Measured, not assumed: collapsing only Export/Import/Sign out and leaving the sync pill and Auto-plan CTA full-size still doesn't reliably fit one line at 390px — those two alone are close to half the row's width budget. Collapsing the sync pill too gets it close, but still isn't a guaranteed single line on every device/zoom level (see the fold marker on the mobile frame below for the honest outcome, not an assertion). Either way the order doesn't change — tabs stay 4th — so this variant reduces the chrome's height/width, it doesn't reposition the tabs the way Variant 1 does.
Route-strip placement: unchanged — stays attached to identity. This variant doesn't touch the stack's order or grouping, only the utility row's density, so there's no new relationship to decide: the strip stays exactly where it is today, inside .topbar alongside trip identity.

Variant 3 — bottom tab bar on mobile, top tabs on desktopchosen

Standard installed-PWA pattern: on small screens the primary nav relocates to a thumb-reach dock fixed to the bottom of the viewport (position:fixed in the real app; env(safe-area-inset-bottom) reserved so it clears the iOS home indicator, and <main> gets matching bottom padding so content never sits behind it). Desktop tabs stay at the top — unchanged from here. Desktop header chrome itself is no longer left as-is though: see the condensing-header refinement just below, added after this variant was picked, to answer "the day chips and Add place button disappear on desktop too."
Route-strip placement: stays with identity at the top (forced, not a free choice). On mobile the primary nav physically relocates to the bottom of the screen — it's no longer adjacent to anything at the top, so "attach the strip to primary nav" isn't an available option here the way it was in Variant 1. The strip stays in .topbar next to identity, sticky at the top, functioning as a second top-of-screen nav layer independent from the bottom tab dock. Desktop keeps the current relationship (strip under identity, tabs below that) unchanged, since desktop nav never moves in this variant.

Open risk, not yet resolved: keyboard focus order skips past the whole panel first. In buildV3Mobile the bottom tab dock is the LAST thing in DOM order — after every filler row in <main>. A mouse or touch user reaches it instantly (it's pinned to the bottom of the screen), but a keyboard-only user tabbing through the page must pass every focusable element in the panel above before Tab reaches primary navigation at all. The real Map/Places/Itinerary/Budget panels have far more focusable content than this mockup's filler list, so the real gap would be worse than what's shown here. A production implementation would need to either move the nav earlier in DOM order while keeping it visually docked at the bottom (e.g. via CSS order/flex, not full reflow), or add a skip-link. Variant 3 refinement — condensing header (desktop)

Follow-up after Variant 3 was picked: on desktop, leaving the top header exactly as the baseline (as the original comparison did) means the sticky identity block + full utility row + route-strip + tabbar together still occupy a large, fixed share of the viewport — and unlike the header itself, the Map panel's own day-filter chips and "Add place" button are ordinary scrolling content, so they scroll away as soon as you move down toward the map, leaving very little room to both see them and see the map. This section keeps the header sticky but makes it shrink once you've actually started scrolling, giving that space back. Mobile is unaffected — the bottom tab dock from the approved Variant 3 stays exactly as it was; this is a desktop-only addition.
What condenses, and to what. Three things shrink together, all reusing patterns already established elsewhere in this file rather than inventing new ones: (1) the identity block drops its eyebrow and subtitle entirely (display:none, not the visually-hidden technique — there's no longer a control on screen for that text to label) and the title's font-size shrinks, going from a 3-line stack to a single compact line; (2) the utility row collapses to icon-only by reusing Variant 2's exact .is-collapsed treatment verbatim (Export / Import / Sign out / sync pill), extended here to also cover the Auto-plan CTA (which V2 deliberately left full-size — different context: V2 was optimising a crowded mobile row against a hard 640px width budget, this is a desktop row with plenty of width to spare, so collapsing Auto-plan here is about reclaiming height, not fitting a line); (3) the route-strip's nodes shrink to city-name-only pills, dropping the date sub-line, rather than disappearing (it's still the primary city selector — per Variant 3's own decision-note above, desktop keeps the original identity+route-strip+tabbar relationship, so the strip condensing in place rather than vanishing keeps that relationship coherent instead of quietly breaking it). The tabs themselves never shrink or move — they're the one thing this whole exercise exists to keep prominent.
Day chips get promoted to their own sticky layer; Add place doesn't. The day-filter chips and the Add place button are both Map-tab-specific — they live inside MapPanel.tsx, not the global chrome in App.tsx. That rules out putting them inside the always-sticky topbar/tabbar (which is shared across all 4 tabs): a sticky slot that's sometimes full of day chips and sometimes empty, depending on which tab happens to be active, would make the header's height change on tab-switch as well as on scroll — two independent sources of layout shift stacked on top of each other. Instead, the day chips get their own sticky sub-bar, .map-day-quicknav, positioned right under the (already-sticky) tabbar — this is exactly the same architecture the real app already uses for the Itinerary tab's quick-nav (--itnav-h, src/index.css's .it-quicknav), just applied to Map. It only exists while viewing the Map tab, so the global header's height stays tab-independent; only the Map panel gains a second sticky layer of its own. Add place is deliberately left in normal scrolling flow, not promoted — the map surface already has its own persistent "Tap map to add" affordance (.map-add-hint, floating over the map box itself, position:absolute within .map-stage-wrap) that stays visible for as long as the map is in view, which is most of the scrolled experience once you're actually looking at pins. Promoting the toolbar button too would be solving a problem that's already solved a different way, at the cost of more sticky chrome. This is a visual-parity argument only — see the flagged gap immediately below, it does not extend to keyboard/AT users.
Open gap, not resolved: "Add place" has no keyboard/AT equivalent once scrolled past. The .map-add-hint reasoning above only holds for sighted mouse/touch users. In MapPanel.tsx (~L179) that element is rendered aria-hidden="true", and src/index.css's .map-badge rule (~L340) sets pointer-events:none on it — it's a purely decorative visual cue, not an interactive control, and tapping the map to add a place is a Leaflet click handler, not keyboard-operable either. So once the panel-head scrolls out of view, a keyboard-only or screen-reader user genuinely loses their only route to "add a place" until they scroll all the way back up — there's no equivalent affordance for them the way there is for a sighted mouse user. Same class of problem as the keyboard focus-order gap already flagged under Variant 3's mobile frame above, and not solved here either. A real fix would need an actual keyboard-operable control that stays reachable (e.g. promoting a small icon-only "Add place" button into the condensed utility row, or into .map-day-quicknav alongside the chips) rather than relying on the decorative map hint.

Engineering implications, flagged for whoever implements this.
  • Trigger mechanism: this mockup's live demo drives the condense/expand toggle off a scroll listener (rAF-throttled, two-threshold hysteresis — condense past 88px, re-expand only below 32px, so hovering right at one number can't flap it) because that's the simplest thing to hand-wire reliably against an arbitrary scroll container for a demo. The real implementation should prefer an IntersectionObserver against a thin sentinel element placed just below the identity block, instead of a scroll listener: cheaper (no per-frame scroll-event handling at all), and the sentinel's own height can BE the hysteresis band (condense when it's fully scrolled past, re-expand only once it's fully back in view) rather than needing two hand-tuned pixel constants.
  • Composes with useStickyOffsets for free: that hook already measures .topbar's real offsetHeight via ResizeObserver and writes it to --topbar-h (see src/hooks/useStickyOffsets.ts) — since the condense transition changes .topbar's actual rendered height, the existing observer picks that up automatically and .tabbar / the new .map-day-quicknav (both positioned off --topbar-h) reflow to match with no new plumbing. The real cost: the observer fires on every intermediate layout during the ~220ms CSS transition, so the dependent elements' top offset is recomputed continuously while it animates — desirable (it should track smoothly), but worth an actual perf profile on lower-end hardware before shipping, since it's repeated layout work on every scroll transition rather than a one-off.
  • Must be gated to the same desktop/mobile breakpoint Variant 3 already uses: nothing in .topbar.can-condense/.is-condensed is itself scoped to a min-width media query — in this mockup "desktop-only" holds only because buildV3CondenseDesktop() is never mounted inside a .phone-frame and wireCondenseHeader() is never called there. The real implementation needs to gate initialisation (attaching the observer, adding .can-condense in the first place) behind the exact same breakpoint that already switches Variant 3 between top-tabs-desktop and bottom-dock-mobile — otherwise a resize or tablet rotation near that boundary could leave the condensing header active at the same time as the mobile bottom dock, which was never designed to coexist with it.
  • Not modelled here: what happens when the trip title is long enough to wrap even in the condensed single-line state (i18n / a very long custom trip name), and whether the condense transition should be skipped entirely below a certain viewport height where the expanded state barely fits anyway. Both are open questions, not resolved by this mockup.
